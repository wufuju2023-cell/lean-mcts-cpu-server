## 5. 与「原始管线」对照（96.7% 时间在 Lean，25.9s/attempt）

- 原始：每次评测 attempt = 整文件独立编译（云端均值 25.9s，Lean 占 96.7%）；串行 103 attempts ≈ 47 min。
- 新架构：一次会话启动（≈ 一次整文件 import），之后所有战术交互是**增量 apply（ms 级）+ 会话内内核复验**；
  同机对照：整文件编译 5.54s ↔ 会话稳态求解 0.30s（Pell 三战术证明），≈18.5×。
- 结构差异（比数字更重要）：旧管线每个 attempt 都是「从零编译」；新管线支持
  **状态句柄 + O(1) 回滚/分支**，使 MCTS 式搜索（大量试错与回滚）第一次变得廉价。
- 边界：会话启动（Mathlib import）仍是固定成本 → 波次场景靠并发掩盖；下一步可用进程池预热复用。

## 6. 关键工程修复（v0 踩坑记录）

1. `lean file.lean`（check 模式）中 elaborator task 线程的 `IO.getStdin` 是空流 → 改为
   re-open `/proc/self/fd/0` 读真实 stdin。
2. 同线程的 stdout 被缓冲（进程退出才 flush）→ 协议输出改走 **FIFO 文件句柄**（`LMC_OUTPUT_FIFO`），实时可达。
3. 失败战术会污染状态 → apply 出错后 `SavedState.restore` 回滚，分支互不干扰（失败路径 1.4ms）。
4. `close` 时未复验 → 恢复初始状态并 `admitGoal` 收尾，shell 文件仍可编译（带 sorry 警告，exit 0）。
